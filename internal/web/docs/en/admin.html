Staff, settings and updates

Staff accounts

  • Administrators may do everything, including staff accounts and server settings.
  • Operators manage packages, customers, domains and mailboxes.
  • Viewers only look.

Every account signs in with a password and an authenticator app. The audit log records every change; each entry is chained to the previous one by a hash, so later edits of the log are detected.

Mail server settings

  • Host name: the full name of the server (e.g. mail.example.com). It must resolve to the server's public address, and that address should resolve back to it (PTR record at your hosting provider); otherwise other servers treat your mail as spam.
  • Largest message for incoming and outgoing mail.
  • Domain verification and dedicated server: see Domains, mailboxes and aliases.

How the server is built

The panels run as the unprivileged user emailzit. A small mail helper runs as root and does only a fixed list of tasks: write the Postfix and Dovecot configuration from the server settings (checked before it is used, the old files are put back on any error), create the mail directory of a new customer, move the mail of deleted mailboxes to the trash. Postfix and Dovecot read domains, mailboxes and app passwords directly from PostgreSQL through read-only views, so customer input never reaches a configuration file.

Network and sign-in

The panels listen on port 8444 (HostZit uses 8443). Allowed networks, session length and the blocking of addresses after failed sign-ins are under Settings. If you lock yourself out: emailzit-server --reset-allowlist or --unblock-ip ADDRESS on the server.

Protection of mail sign-ins and sending

  • Password guessing: Dovecot asks EmailZit before every sign-in of a mail program (IMAP, POP3 and SMTP submission). An address with 10 failed sign-ins within 15 minutes is refused and blocked in the firewall for an hour (ports 110, 143, 465, 587, 993, 995, 4190 and 8444; port 25 stays open for other mail servers). An account attacked from many addresses is slowed down, never locked, so attackers cannot lock users out.
  • Sending limits per mailbox and per customer come from the package. Each recipient counts. Messages over the limit get a temporary error and the mail program tries again later. A mailbox that keeps trying far beyond its limit (30 refused attempts in an hour) is blocked from sending automatically; the block is in the audit log and staff lift it on the mailbox page.
  • Spam filter: Rspamd checks every incoming message; clear spam is refused, likely spam goes to the Junk folder (how likely is set per customer and per mailbox, see Mail → Spam settings). Mail of signed-in users is signed with the domain's DKIM key.

Company sign-in for staff

Under Settings → Company sign-in staff can sign in with the company's identity provider (OpenID Connect: Microsoft Entra ID, Google Workspace, Keycloak, Authentik …): register EmailZit there as a web application with the redirect address shown on the page, then enter the issuer, client ID and client secret. The provider proves the e-mail address; a staff account whose username is exactly that address must already exist (no accounts are created; customers and mail users always use their password). The web always needs a second factor: EmailZit asks its own code unless Trust the provider's second factor is on and the identity token says that the provider asked one (amr with mfa, otp, hwk …). Disabling the staff account in EmailZit locks the person out at once, whatever the provider says.

REST API for billing

Under Settings → REST API administrators create tokens for billing systems (for example the MaxZit portal) and HostZit. A token has only the permissions it is given (customers:read, customers:write, usage:read, sso:create), may be limited to addresses and expires. The page lists all calls; customers are addressed by their UUID or by ext:<billing ID>; create calls accept an Idempotency-Key so a repeated call does not create a second customer. POST /api/v1/customers/{id}/sso returns a one-time link (60 seconds) that signs the customer in to the customer panel. Every call is in the audit log as api:<token name>.

Backup of the panel

Settings → Backup of the panel writes an encrypted file every day (and on demand) with the database, the secret key of the server and the panel certificate, keeps the newest ones and can copy them to an SFTP folder. The mail itself (/var/vmail) is backed up with BackupZit. To restore: stop emailzit-server, run emailzit-server -restore FILE -restore-passphrase-file FILE as user emailzit, start the services again; the mail configuration and the DKIM keys are written again at start.

Together with HostZit

When HostZit hosts the websites and the DNS of the same customers, link the two under Settings → HostZit: the address of HostZit's admin panel and a HostZit API token with the permission dns:mail. EmailZit then writes the mail records of every domain (MX, SPF, DKIM, DMARC, MTA-STS, autoconfig) into HostZit's DNS by itself and keeps them current when the host name or a DKIM key changes; a domain whose zone HostZit hosts for the same customer needs no TXT verification. If the customer already has own records with the same names in HostZit, they are kept and the domain page says so. The sidebar gets a switch to HostZit.

Mail from websites. HostZit needs an EmailZit API token with customers:write to tell EmailZit the Linux user IDs of each customer's hosting accounts (PUT /api/v1/customers/{id}/web-uids). PHP's mail() on those accounts runs /usr/sbin/emailzit-sendmail, which hands the message to EmailZit over /run/emailzit/submit.sock. EmailZit knows the account by the user ID of the process, takes mail only from registered accounts of active customers, lets a website send only as addresses of the customer's own verified domains (Date and Message-ID are added when missing), counts each hosting account like a mailbox under the package's limits (per hour, per day, recipients per message, and the customer limit together with the mailboxes), and passes the message to Postfix, where it is DKIM-signed; the delivery log shows it as web-<user ID>. A hosting account that keeps trying beyond its limit (a hacked website sending spam) is blocked automatically; the customer page lists the accounts with their counts and lifts or sets the block. Programs on the server cannot use Postfix's own sendmail (only root may), and port 25 trusts no local program.
