Staff, settings and updates

Staff accounts

  • Administrators may do everything, including staff accounts and server settings.
  • Operators manage packages, customers, domains and mailboxes.
  • Viewers only look.

Every account signs in with a password and an authenticator app. The audit log records every change; each entry is chained to the previous one by a hash, so later edits of the log are detected.

Mail server settings

  • Host name: the full name of the server (e.g. mail.example.com). It must resolve to the server's public address, and that address should resolve back to it (PTR record at your hosting provider); otherwise other servers treat your mail as spam. Check under Host name and PTR records shows, for every address the server sends from (IPv4 and IPv6), whether the host name points at it and its PTR record points back.
  • Send mail to other servers over IPv4 only: for a server with IPv6 whose provider cannot set a PTR record for the IPv6 address (Gmail and Outlook refuse such mail). Receiving over IPv6 keeps working.
  • Largest message for incoming and outgoing mail.
  • Virus scan: ClamAV checks every message and infected mail is refused ("Virus found"). Switching it on installs ClamAV by itself (about 1 GB of memory); the scan starts when the virus signatures are downloaded, a few minutes later. Switching it off stops ClamAV again. With Sanesecurity's free signatures ClamAV also knows current spam, phishing, scam and malicious-link messages and dangerous macros: the mail helper downloads them every six hours from Sanesecurity's mirrors and installs a file only when its GPG signature checks out against Sanesecurity's key. Their spam signatures only add 7 to the spam score (the message goes to Junk); everything else counts as a virus. The signatures are free to use; Sanesecurity asks companies for a donation.
  • Risky attachments (on by default): programs, scripts, shortcuts, disk images and Office files with macros (.exe, .js, .vbs, .bat, .lnk, .iso, .docm, .xlsm and similar) are refused in both directions, also inside ZIP and other archives; the sender is told to share such files by link.
  • Forged senders (on by default): a domain whose DMARC policy says p=reject states that mail which passes neither SPF nor DKIM does not come from it. Such mail is refused ("The sender domain refuses this mail (DMARC)"), and mail from a domain with p=quarantine goes to Junk; the large providers do the same. Mailing lists and forwarded mail break DMARC by nature and are left to the spam score.
  • Notices for administrators: up to five addresses. They get a weekly report on Monday morning (mail received, sent, deferred, bounced and refused, the mailboxes that sent most, automatic blocks, the block-list state of the server's addresses), a notice when an address of the server lands on a DNS block list or comes off it (checked every six hours), and a notice when a mailbox is blocked for sending spam. The notices come from postmaster@ the host name.
  • Outbound addresses: extra IP addresses of the server for outgoing mail, one per line with its own host name (203.0.113.5 mail2.example.com). Give a customer one on the customer's page (Outbound address): the customer's mail then leaves from that address and greets with that host name, so one customer who sends spam cannot spoil the reputation of the others. The address must be configured on the server (otherwise the mail leaves from the main address), its host name must point at it and its PTR record must name the host name. The SPF record suggested on each of the customer's domains then names the address (v=spf1 mx ip4:203.0.113.5 ~all); with HostZit hosting the zone it is updated by itself. Not used together with a smart host.
  • Smart host: only when the provider blocks port 25 or wants all mail through its own server — every outgoing message then goes to that server (port 587 with STARTTLS by default, 465 with TLS from the start). With a user name the login always goes over TLS; the password is stored sealed in the panel and as a root-only file for Postfix.
  • Domain verification and dedicated server: see Domains, mailboxes and aliases.

How the server is built

The panels run as the unprivileged user emailzit. A small mail helper runs as root and does only a fixed list of tasks: write the Postfix and Dovecot configuration from the server settings (checked before it is used, the old files are put back on any error), create the mail directory of a new customer, move the mail of deleted mailboxes to the trash. Postfix and Dovecot read domains, mailboxes and app passwords directly from PostgreSQL through read-only views, so customer input never reaches a configuration file.

Network and sign-in

The panels listen on port 8444 (HostZit uses 8443). Allowed networks, session length and the blocking of addresses after failed sign-ins are under Settings. If you lock yourself out: emailzit-server --reset-allowlist, --unblock-ip ADDRESS or --reset-password USERNAME (new password from standard input, to be changed at the next sign-in) on the server as user emailzit; the appliance's setup menu does the same.

After the installation only private networks and the server itself may reach port 8444. On a server with a public address customers and mail users (webmail) need it too: sign in once through an SSH tunnel (ssh -L 8444:127.0.0.1:8444 root@SERVER, then https://127.0.0.1:8444) and add 0.0.0.0/0 / ::/0 under Network and access. Staff accounts stay protected by the second factor and the blocking after failed sign-ins.

Settings → Updates and server also shows the operating system: waiting Debian updates (checked by itself twice a day), whether automatic security updates are on, and buttons to install all updates and to restart the whole server. On the appliance the SSH server can be switched on or off and moved to another port there (a port the SSH server refuses changes nothing); these and the restart also go through four-eyes approval when it is on.

Protection of mail sign-ins and sending

  • Password guessing: Dovecot asks EmailZit before every sign-in of a mail program (IMAP, POP3 and SMTP submission). An address with 10 failed sign-ins within 15 minutes is refused and blocked in the firewall for an hour (ports 110, 143, 465, 587, 993, 995, 4190 and 8444; port 25 stays open for other mail servers). An account attacked from many addresses is slowed down, never locked, so attackers cannot lock users out. Such a block is listed under Settings → Sign-in and security → Blocked addresses and can be lifted there; it does not stop the panel, so a mail program with an old password cannot lock its owner out.
  • Sending limits per mailbox and per customer come from the package. Each recipient counts. Messages over the limit get a temporary error and the mail program tries again later. A mailbox that keeps trying far beyond its limit (30 refused attempts in an hour) is blocked from sending automatically; the block is in the audit log and staff lift it on the mailbox page.
  • Spam filter: Rspamd checks every incoming message; clear spam is refused, likely spam goes to the Junk folder (how likely is set per customer and per mailbox, see Domains, mailboxes and aliases → Spam settings). Mail of signed-in users is signed with the domain's DKIM key.
  • Spam sent by signed-in users (mail programs, webmail, websites) is refused already at a score of 10, and never marked or delayed. A mailbox whose outgoing mail is refused as spam or virus 3 times within an hour is blocked from sending automatically: almost always someone else knows its password. The administrators get a notice (Settings → Mail server → Notices for administrators), the mailbox gets one in its Inbox in its language, and the block is in the audit log; set a new password and lift the block on the mailbox page.
  • Phishing: messages with links PhishTank knows as phishing, and messages whose display name names a domain of this server while the address is foreign ("Boss acme.com" <someone@freemail.example>), get [Phishing?] in front of the subject, so the warning shows in every mail program.
  • Port 25: postscreen answers first. Servers that talk before the greeting (the usual spam robots) or are on DNS block lists (Spamhaus ZEN alone is enough; SpamCop and PSBL count less; DNSWL lowers the score) are turned away before they reach Postfix. Per address at most 20 connections at once, 60 per minute, 100 messages and 300 recipients per minute.
  • Local DNS resolver: Unbound runs on the server (port 5335) and Rspamd asks it, because DNS block lists refuse queries that come through big public resolvers. Where no other DNS server uses port 53 (HostZit's PowerDNS does), Unbound also answers there and the whole server resolves through it; Postfix then gets DNSSEC-validated answers and sends only over TLS with the certificate named in a receiver's DANE (TLSA) records. The server's own /etc/resolv.conf is kept in /var/lib/emailzit/ and comes back by itself when Unbound stops answering or HostZit is installed.
  • MTA-STS for outgoing mail: domains that publish an MTA-STS policy in enforce mode (Gmail, Outlook and many others) get mail only over TLS, to the servers the policy lists, with a valid certificate. EmailZit looks the policies up and keeps them for their lifetime; where DANE works for the domain, DANE is used instead. Not used with a smart host.

Four-eyes approval

Under Settings → Sign-in and security administrators can turn on four-eyes approval (it needs at least two active administrators). Then risky changes by staff are not done at once but wait under Approvals until another administrator approves them: terminating or suspending a customer, deleting a domain or mailbox, resetting a second factor, creating or changing staff accounts and their passwords, deleting API tokens and backups, and the network, company sign-in and security settings, including turning four-eyes approval off. Nobody can approve their own request (they can withdraw it); an approved change runs once, as the approving administrator, and both names are in the audit log; a request expires after 24 hours. The form values of a waiting request are stored encrypted. Customers changing their own domains and mailboxes, and the REST API, are not affected.

Company sign-in for staff

Under Settings → Company sign-in staff can sign in with the company's identity provider (OpenID Connect: Microsoft Entra ID, Google Workspace, Keycloak, Authentik …): register EmailZit there as a web application with the redirect address shown on the page, then enter the issuer, client ID and client secret. The provider proves the e-mail address; a staff account whose username is exactly that address must already exist (no accounts are created; customers and mail users always use their password). The web always needs a second factor: EmailZit asks its own code unless Trust the provider's second factor is on and the identity token says that the provider asked one (amr with mfa, otp, hwk …). Disabling the staff account in EmailZit locks the person out at once, whatever the provider says.

REST API for billing

Under Settings → REST API administrators create tokens for billing systems (for example the MaxZit portal) and HostZit. A token has only the permissions it is given (customers:read, customers:write, usage:read, sso:create), may be limited to addresses and expires. The page lists all calls; customers are addressed by their UUID or by ext:<billing ID>; create calls accept an Idempotency-Key so a repeated call does not create a second customer. POST /api/v1/customers/{id}/sso returns a one-time link (60 seconds) that signs the customer in to the customer panel. Every call is in the audit log as api:<token name>.

Backup of the panel

Settings → Backup of the panel writes an encrypted file every day (and on demand) with the database, the secret key of the server and the panel certificate, keeps the newest ones and can copy them to an SFTP folder. The mail itself (/var/vmail) is backed up with BackupZit. To restore: stop emailzit-server, run emailzit-server -restore FILE -restore-passphrase-file FILE as user emailzit, start the services again; the mail configuration and the DKIM keys are written again at start.

Export, BackupZit and WatchZit

Export on the customer page (or POST /api/v1/customers/{id}/export) packs all mail of the customer and a manifest.json with the settings (domains, mailboxes, aliases, auto-replies and filters, spam settings) into /var/lib/emailzit/exports/<customer>/<time>.tar.gz; passwords, app passwords, second factors and DKIM keys are left out. It runs in the background (the API answers with a job: GET /api/v1/jobs/{id}); the newest three exports of a customer are kept and can be downloaded from the page or with GET /api/v1/customers/{id}/exports/{name}. BackupZit can back up that folder together with the panel backup, or the whole /var/vmail. WatchZit checks the server with GET /api/v1/server/status (token with customers:read): state of Postfix, Dovecot, Rspamd, Valkey and the website mail socket, messages in the queue and deferred, free disk of the mail store and the days until the certificate expires; ok is false when a service is not active.

Import on the customer page (or POST /api/v1/customers/{id}/import?format=emailzit|cpanel with the .tar.gz as the body) takes an EmailZit export or a cPanel account backup (cpmove-USER.tar.gz; HostZit passes the mail part of its cPanel import this way). Missing domains (the domain must not belong to another customer), mailboxes and forwarders are created within the package limits (a quota that does not fit becomes the package default), then the root helper copies the Maildirs in: only into mailboxes of that customer, never overwriting a file, never following links, without Dovecot indexes and the old quota file (both are rebuilt). cPanel passwords are not taken over: each mailbox gets a random password, so set one for every user (mail programs then use app passwords). From cPanel the mail of the domain mailboxes, their quotas and the forwarders are taken; the main account's own mailbox, pipes to programs and the catch-all are listed as notes. From an EmailZit export also the spam settings and the stored auto-replies and filters come along (they start working when the user saves them once). The result and the notes are shown on the customer page and in the job (GET /api/v1/jobs/{id}, field report).

Together with HostZit

When HostZit hosts the websites and the DNS of the same customers, link the two under Settings → HostZit with a pairing code (below). EmailZit then writes the mail records of every domain (MX, SPF, DKIM, DMARC, MTA-STS, autoconfig) into HostZit's DNS by itself and keeps them current when the host name or a DKIM key changes; a domain whose zone HostZit hosts for the same customer needs no TXT verification. If the customer already has own records with the same names in HostZit, they are kept and the domain page says so. The sidebar gets a switch to HostZit. On a server with both products HostZit's web server answers on ports 80 and 443; EmailZit writes its own part (/etc/nginx/zit.d/emailzit/) for autoconfig., autodiscover. and mta-sts. of every domain, with only the paths mail programs and MTA-STS use; the panels are never reachable there.

Mail from websites. HostZit needs an EmailZit API token with customers:write to tell EmailZit the Linux user IDs of each customer's hosting accounts (PUT /api/v1/customers/{id}/web-uids). PHP's mail() on those accounts runs /usr/sbin/emailzit-sendmail, which hands the message to EmailZit over /run/emailzit/submit.sock. EmailZit knows the account by the user ID of the process, takes mail only from registered accounts of active customers, lets a website send only as addresses of the customer's own verified domains (Date and Message-ID are added when missing), counts each hosting account like a mailbox under the package's limits (per hour, per day, recipients per message, and the customer limit together with the mailboxes), and passes the message to Postfix, where it is DKIM-signed; the delivery log shows it as web-<user ID>. A hosting account that keeps trying beyond its limit (a hacked website sending spam) is blocked automatically; the customer page lists the accounts with their counts and lifts or sets the block. Programs on the server cannot use Postfix's own sendmail (only root may), and port 25 trusts no local program.

Linking with a pairing code. Settings → HostZit → Make a pairing code shows a code once; paste it into HostZit under Settings → EmailZit. The code works once and only for ten minutes, EmailZit keeps only its hash, and it never reaches a log. The two servers then hand each other a token of their own, each with the least permissions and bound to the addresses of the other server, so nobody copies a token by hand. Afterwards the page says which server is linked, since when, and from which addresses its token works. Unlink on either side revokes both tokens; if the other server cannot be reached, the link ends here and the page says to remove it there as well. A link typed in by hand (HostZit's address and a dns:mail token) keeps working. HostZit's addresses have to reach this panel, which on a hosting server they do.

Mail from websites on another server. When HostZit runs on a server of its own, its websites cannot reach the socket above, so the pairing also hands over a relay login: host name, port 2587, user name and password. EmailZit's own submission server takes their mail there, after STARTTLS and that sign-in. The port is open only while such a link exists and only for the addresses of that HostZit, and the login works nowhere else: not for a mailbox, the webmail or a mail program. Every message is checked: the envelope sender must be a mail domain of this server or a domain HostZit hosts for one of its customers (EmailZit asks HostZit once and remembers the answer for ten minutes; an unknown domain is refused with 550, and while HostZit cannot be asked the answer is 451, so the website tries again later), and the From address must use that same domain. The customer's package limits count this mail together with the mailboxes; a domain whose customer is not in EmailZit may send 200 recipients an hour. The message then goes the way of a website on this server: DKIM signature, outgoing spam check, delivery log. The customer's page lists this mail with what became of it, the weekly report counts it, and Settings → HostZit shows the login with its last use.
