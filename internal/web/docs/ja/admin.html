スタッフ、設定、更新

スタッフアカウント

  • 管理者は、スタッフアカウントとサーバー設定を含むすべての操作ができます。
  • オペレーターはパッケージ、顧客、ドメイン、メールボックスを管理します。
  • 閲覧者は閲覧のみです。

すべてのアカウントはパスワードと認証アプリでサインインします。監査ログはすべての変更を記録します。各エントリーはハッシュで前のエントリーと連結されているため、後からログが編集されると検出されます。

メールサーバーの設定

  • ホスト名：サーバーの完全な名前です（例：mail.example.com）。この名前はサーバーのパブリックアドレスに解決され、そのアドレスは逆にこの名前に解決される必要があります（ホスティングプロバイダーでの PTR レコード）。そうでないと、他のサーバーはあなたのメールをスパムとして扱います。ホスト名と PTR レコードのチェックは、サーバーが送信に使うすべてのアドレス（IPv4 と IPv6）について、ホスト名がそのアドレスを指しているか、PTR レコードがホスト名を指し返しているかを表示します。
  • 他のサーバーへのメール送信は IPv4 のみ：IPv6 を持つものの、プロバイダーが IPv6 アドレスに PTR レコードを設定できないサーバー向けです（Gmail と Outlook はそのようなメールを拒否します）。IPv6 での受信は引き続き機能します。
  • 最大のメッセージ：受信メールと送信メールの最大サイズです。
  • ウイルススキャン：ClamAV がすべてのメッセージを検査し、感染したメールは拒否されます（"Virus found"）。オンにすると ClamAV が自動的にインストールされ（メモリ約 1 GB）、ウイルスシグネチャがダウンロードされる数分後にスキャンが始まります。オフにすると ClamAV は再び停止します。Sanesecurity の無料シグネチャを使うと、ClamAV は最新のスパム、フィッシング、詐欺、悪意のあるリンクを含むメッセージや危険なマクロも認識します。メールヘルパーは 6 時間ごとに Sanesecurity のミラーからシグネチャをダウンロードし、GPG 署名が Sanesecurity の鍵で正しく検証された場合にのみファイルをインストールします。スパムシグネチャはスパムスコアに 7 を加算するだけです（メッセージは Junk に入ります）。それ以外はすべてウイルスとして扱われます。シグネチャは無料で使用できます。Sanesecurity は企業に寄付をお願いしています。
  • 危険な添付ファイル（既定でオン）：プログラム、スクリプト、ショートカット、ディスクイメージ、マクロ付き Office ファイル（.exe、.js、.vbs、.bat、.lnk、.iso、.docm、.xlsm など）は、ZIP やその他のアーカイブ内にあるものも含め、送受信の両方向で拒否されます。送信者には、そのようなファイルをリンクで共有するよう案内されます。
  • 偽装された送信者（既定でオン）：DMARC ポリシーが p=reject のドメインは、SPF も DKIM も通らないメールは自分からのものではないと宣言しています。そのようなメールは拒否され（「The sender domain refuses this mail (DMARC)」）、p=quarantine のドメインからのメールは迷惑メールフォルダーに入ります。大手プロバイダーも同じようにしています。メーリングリストや転送されたメールは性質上 DMARC を壊すため、迷惑メール判定の点数に任せます。
  • 管理者への通知：最大 5 つのアドレスです。これらのアドレスには、月曜日の朝に週次レポート（受信、送信、保留、返送、拒否されたメール、最も多く送信したメールボックス、自動ブロック、サーバーのアドレスのブロックリスト状況）が届き、サーバーのアドレスが DNS ブロックリストに載ったとき、またはリストから外れたとき（6 時間ごとに確認）、およびメールボックスがスパム送信でブロックされたときに通知が届きます。通知はホスト名の postmaster@ から送られます。
  • 送信元アドレス一覧：送信メール用のサーバーの追加 IP アドレスです。1 行に 1 つ、専用のホスト名と共に記述します（203.0.113.5 mail2.example.com）。顧客のページ（送信元アドレス）で顧客に 1 つ割り当てると、その顧客のメールはそのアドレスから送信され、そのホスト名で挨拶するため、スパムを送る 1 つの顧客が他の顧客の評判を損なうことはありません。アドレスはサーバーに設定されている必要があり（設定されていない場合、メールはメインのアドレスから送信されます）、ホスト名はそのアドレスを指し、PTR レコードはホスト名を示している必要があります。その後、顧客の各ドメインに推奨される SPF レコードにこのアドレスが含まれます（v=spf1 mx ip4:203.0.113.5 ~all）。HostZit がゾーンをホストしている場合は、自動的に更新されます。スマートホストとは併用されません。
  • スマートホスト：プロバイダーがポート 25 をブロックしている場合や、すべてのメールを自社のサーバー経由にしたい場合のみ使います。その場合、すべての送信メッセージはそのサーバーに送られます（既定ではポート 587 と STARTTLS、465 では最初から TLS）。ユーザー名を指定すると、ログインは常に TLS 経由で行われます。パスワードはパネル内に封印して保存され、Postfix 用に root のみが読めるファイルとしても保存されます。
  • ドメイン確認と専用サーバー：「ドメイン、メールボックス、エイリアス」を参照してください。

サーバーの構成

パネルは特権のないユーザー emailzit として動作します。小さなメールヘルパーが root として動作し、決められた一連の処理だけを行います。サーバー設定から Postfix と Dovecot の設定を書き出す（使用前に検査し、エラーがあれば古いファイルに戻します）、新しい顧客のメールディレクトリを作成する、削除されたメールボックスのメールをごみ箱に移す、といった処理です。Postfix と Dovecot は、ドメイン、メールボックス、アプリパスワードを読み取り専用ビューを通じて PostgreSQL から直接読み取るため、顧客の入力が設定ファイルに届くことはありません。

ネットワークとサインイン

パネルはポート 8444 で待ち受けます（HostZit は 8443 を使用）。許可するネットワーク、セッションの長さ、サインインに失敗したアドレスのブロックは設定にあります。自分自身を締め出してしまった場合は、サーバー上でユーザー emailzit として emailzit-server --reset-allowlist、--unblock-ip ADDRESS、または --reset-password USERNAME（新しいパスワードは標準入力から渡し、次回のサインイン時に変更が必要）を実行します。アプライアンスのセットアップメニューでも同じことができます。

インストール直後は、ポート 8444 に接続できるのはプライベートネットワークとサーバー自身だけです。公開アドレスを持つサーバーでは、顧客とメールユーザー（Web メール）も接続する必要があります。一度 SSH トンネル経由でサインインし（ssh -L 8444:127.0.0.1:8444 root@SERVER、続いて https://127.0.0.1:8444）、ネットワークとアクセスに 0.0.0.0/0 / ::/0 を追加してください。スタッフのアカウントは引き続き二要素認証とサインイン失敗後のブロックで保護されます。

設定 → アップデートとサーバーには OS の情報も表示されます。保留中の Debian アップデート（1 日 2 回自動的に確認）、自動セキュリティアップデートがオンかどうか、そしてすべてのアップデートをインストールするボタンとサーバー全体を再起動するボタンです。アプライアンスでは、ここで SSH サーバーのオン・オフを切り替えたり、別のポートに移したりできます（SSH サーバーが受け付けないポートを指定しても何も変わりません）。4 つの目による承認がオンの場合、これらの操作と再起動も承認を経由します。

メールのサインインと送信の保護

  • パスワードの推測：Dovecot は、メールソフトのサインイン（IMAP、POP3、SMTP サブミッション）のたびに EmailZit に問い合わせます。15 分以内に 10 回サインインに失敗したアドレスは拒否され、ファイアウォールで 1 時間ブロックされます（ポート 110、143、465、587、993、995、4190、8444。ポート 25 は他のメールサーバーのために開いたままです）。多数のアドレスから攻撃されたアカウントは速度を落とされますが、ロックされることはないため、攻撃者がユーザーを締め出すことはできません。このブロックは 設定 → サインインとセキュリティ → ブロックされたアドレス に表示され、そこで解除できます。コンソールはブロックしないので、古いパスワードのメールソフトが利用者を締め出すことはありません。
  • 送信制限はメールボックスごと、顧客ごとにパッケージから決まります。宛先 1 件ごとに数えられます。制限を超えたメッセージは一時エラーとなり、メールソフトが後で再試行します。制限を大きく超えて送信を試み続けるメールボックス（1 時間に 30 回拒否された場合）は自動的に送信をブロックされます。ブロックは監査ログに記録され、スタッフはメールボックスのページで解除します。
  • スパムフィルター：Rspamd がすべての受信メッセージを検査します。明らかなスパムは拒否され、スパムの可能性が高いものは Junk フォルダーに入ります（どの程度で振り分けるかは顧客ごと、メールボックスごとに設定します。ドメイン、メールボックス、エイリアス → スパム設定を参照）。サインインしたユーザーのメールは、ドメインの DKIM キーで署名されます。
  • サインインしたユーザーが送信するスパム（メールソフト、Web メール、Web サイト）は、スコア 10 の時点で拒否され、印付けや遅延の扱いはありません。送信メールが1 時間以内に 3 回スパムまたはウイルスとして拒否されたメールボックスは、自動的に送信をブロックされます。ほとんどの場合、他の誰かがそのパスワードを知っています。管理者に通知が届き（設定 → メールサーバー → 管理者への通知）、メールボックスにはその言語で受信トレイに通知が届き、ブロックは監査ログに記録されます。新しいパスワードを設定し、メールボックスのページでブロックを解除してください。
  • フィッシング：PhishTank がフィッシングとして把握しているリンクを含むメッセージや、表示名にこのサーバーのドメインが含まれているのにアドレスが外部のもの（"Boss acme.com" <someone@freemail.example>）であるメッセージには、件名の前に [Phishing?] が付くため、どのメールソフトでも警告が表示されます。
  • ポート 25：最初に postscreen が応答します。挨拶の前に話し始めるサーバー（一般的なスパムロボット）や DNS ブロックリストに載っているサーバー（Spamhaus ZEN だけで十分です。SpamCop と PSBL の重みは低く、DNSWL はスコアを下げます）は、Postfix に届く前に追い返されます。アドレスごとに同時接続は最大 20、1 分あたり 60 接続、1 分あたり 100 メッセージ、300 宛先までです。
  • ローカル DNS リゾルバー：サーバー上で Unbound が動作し（ポート 5335）、Rspamd はこれに問い合わせます。DNS ブロックリストは大手の公開リゾルバー経由の問い合わせを拒否するためです。ポート 53 を使う DNS サーバーが他にない場合（HostZit の PowerDNS は使用します）、Unbound はそちらでも応答し、サーバー全体がこれを通じて名前解決します。その場合 Postfix は DNSSEC で検証された応答を受け取り、受信側の DANE（TLSA）レコードに指定された証明書を使った TLS でのみ送信します。サーバー自身の /etc/resolv.conf は /var/lib/emailzit/ に保存され、Unbound が応答しなくなったときや HostZit がインストールされたときに自動的に元に戻ります。
  • 送信メールの MTA-STS：enforce モードの MTA-STS ポリシーを公開しているドメイン（Gmail、Outlook など多数）には、ポリシーに記載されたサーバーへ、有効な証明書を使った TLS でのみメールを送ります。EmailZit はポリシーを取得し、その有効期間中保持します。そのドメインで DANE が機能する場合は、代わりに DANE が使われます。スマートホストとは併用されません。

4 つの目による承認

設定 → サインインとセキュリティで、管理者は4 つの目による承認をオンにできます（有効な管理者が 2 人以上必要です）。オンにすると、スタッフによるリスクの高い変更はすぐには実行されず、別の管理者が承認するまで承認で待機します。対象は、顧客の解約または停止、ドメインまたはメールボックスの削除、2 つ目の要素のリセット、スタッフアカウントとそのパスワードの作成・変更、API トークンとバックアップの削除、そしてネットワーク、会社アカウントでのサインイン、セキュリティの設定（4 つの目による承認をオフにすることも含む）です。自分自身のリクエストは誰も承認できません（取り下げることはできます）。承認された変更は承認した管理者として 1 回だけ実行され、両者の名前が監査ログに記録されます。リクエストは 24 時間で期限切れになります。待機中のリクエストのフォーム値は暗号化して保存されます。顧客が自分のドメインやメールボックスを変更する操作と REST API は対象外です。

スタッフ向けの会社アカウントサインイン

設定 → 会社アカウントでサインインで、スタッフが会社の ID プロバイダー（OpenID Connect：Microsoft Entra ID、Google Workspace、Keycloak、Authentik …）でサインインできるようにします。プロバイダー側で EmailZit を Web アプリケーションとして登録し、ページに表示されるリダイレクトアドレスを指定してから、発行者（issuer）、クライアント ID、クライアントシークレットを入力します。プロバイダーはメールアドレスを証明します。ユーザー名がそのアドレスと完全に一致するスタッフアカウントがあらかじめ存在している必要があります（アカウントは作成されません。顧客とメールユーザーは常にパスワードを使います）。Web では常に 2 つ目の要素が必要です。プロバイダーの第 2 要素を信頼するがオンで、かつ ID トークンがプロバイダーが要素を求めたことを示している場合（mfa、otp、hwk … を含む amr）を除き、EmailZit は独自のコードを求めます。EmailZit でスタッフアカウントを無効にすると、プロバイダーの判断にかかわらず、その人は直ちに締め出されます。

課金向け REST API

設定 → REST APIで、管理者は課金システム（MaxZit ポータルなど）と HostZit 用のトークンを作成します。トークンには付与した権限（customers:read、customers:write、usage:read、sso:create）だけがあり、アドレスで制限でき、有効期限があります。ページにはすべての呼び出しが一覧表示されます。顧客は UUID または ext:<billing ID> で指定します。作成の呼び出しは Idempotency-Key を受け付けるため、同じ呼び出しを繰り返しても 2 人目の顧客は作成されません。POST /api/v1/customers/{id}/sso は、顧客を顧客パネルにサインインさせる 1 回限りのリンク（60 秒）を返します。すべての呼び出しは api:<token name> として監査ログに記録されます。

パネルのバックアップ

設定 → パネルのバックアップは、データベース、サーバーの秘密鍵、パネルの証明書を含む暗号化されたファイルを毎日（および必要なときに）書き出し、最新のものを保持し、SFTP フォルダーにコピーすることもできます。メール本体（/var/vmail）は BackupZit でバックアップします。復元するには、emailzit-server を停止し、ユーザー emailzit として emailzit-server -restore FILE -restore-passphrase-file FILE を実行してから、サービスを再び起動します。メール設定と DKIM キーは起動時に書き直されます。

エクスポート、BackupZit、WatchZit

顧客のページのエクスポート（または POST /api/v1/customers/{id}/export）は、顧客のすべてのメールと、設定（ドメイン、メールボックス、エイリアス、自動返信とフィルター、スパム設定）を含む manifest.json を /var/lib/emailzit/exports/<customer>/<time>.tar.gz にまとめます。パスワード、アプリパスワード、2 つ目の要素、DKIM キーは含まれません。処理はバックグラウンドで実行され（API はジョブで応答します：GET /api/v1/jobs/{id}）、顧客ごとに最新の 3 件のエクスポートが保持され、ページから、または GET /api/v1/customers/{id}/exports/{name} でダウンロードできます。BackupZit は、このフォルダーをパネルのバックアップと一緒に、または /var/vmail 全体をバックアップできます。WatchZit は GET /api/v1/server/status（customers:read 付きのトークン）でサーバーを監視します。Postfix、Dovecot、Rspamd、Valkey、Web サイトのメールソケットの状態、キュー内および保留中のメッセージ、メールストアの空きディスク容量、証明書の有効期限までの日数です。サービスが有効でない場合、ok は false になります。

顧客のページのインポート（または本文に .tar.gz を付けた POST /api/v1/customers/{id}/import?format=emailzit|cpanel）は、EmailZit エクスポートまたは cPanel アカウントバックアップ（cpmove-USER.tar.gz。HostZit は cPanel インポートのメール部分をこの方法で渡します）を取り込みます。不足しているドメイン（ドメインが他の顧客に属していてはいけません）、メールボックス、転送がパッケージの制限内で作成され（収まらないクォータはパッケージの既定値になります）、その後 root ヘルパーが Maildir をコピーします。コピー先はその顧客のメールボックスのみで、ファイルを上書きせず、リンクをたどらず、Dovecot のインデックスと古いクォータファイルは含めません（どちらも再構築されます）。cPanel のパスワードは引き継がれません。各メールボックスにはランダムなパスワードが設定されるので、ユーザーごとにパスワードを設定してください（その後メールソフトはアプリパスワードを使います）。cPanel からは、ドメインのメールボックスのメール、そのクォータ、転送が取り込まれます。メインアカウント自身のメールボックス、プログラムへのパイプ、キャッチオールは注記として一覧表示されます。EmailZit エクスポートからは、スパム設定と保存されている自動返信とフィルターも取り込まれます（ユーザーが一度保存すると機能し始めます）。結果と注記は、顧客のページとジョブ（GET /api/v1/jobs/{id}、フィールド report）に表示されます。

HostZit との連携

HostZit が同じ顧客の Web サイトと DNS をホストしている場合は、設定 → HostZitで 2 つを連携させます。HostZit 管理パネルのアドレスと、dns:mail 権限付きの HostZit API トークンを指定します。すると EmailZit は、すべてのドメインのメール用レコード（MX、SPF、DKIM、DMARC、MTA-STS、autoconfig）を HostZit の DNS に自動的に書き込み、ホスト名や DKIM キーが変わったときも最新の状態に保ちます。HostZit が同じ顧客のためにゾーンをホストしているドメインは、TXT による確認が不要です。顧客が HostZit に同じ名前の独自のレコードをすでに持っている場合、それらは保持され、ドメインのページにその旨が表示されます。サイドバーには HostZit への切り替えボタンが追加されます。両方の製品があるサーバーでは、HostZit の Web サーバーがポート 80 と 443 で応答します。EmailZit は、すべてのドメインの autoconfig.、autodiscover.、mta-sts. 用に独自の部分（/etc/nginx/zit.d/emailzit/）を書き込みます。含まれるのはメールソフトと MTA-STS が使うパスだけで、パネルにそこからアクセスすることは決してできません。

ウェブサイトからのメール。HostZit は、各顧客のホスティングアカウントの Linux ユーザー ID を EmailZit に伝えるために、customers:write 付きの EmailZit API トークンを必要とします（PUT /api/v1/customers/{id}/web-uids）。これらのアカウントでの PHP の mail() は /usr/sbin/emailzit-sendmail を実行し、これが /run/emailzit/submit.sock を通じてメッセージを EmailZit に渡します。EmailZit はプロセスのユーザー ID でアカウントを識別し、有効な顧客の登録済みアカウントからのメールだけを受け付け、Web サイトには顧客自身の確認済みドメインのアドレスとしてのみ送信を許可し（Date と Message-ID がない場合は追加します）、各ホスティングアカウントをパッケージの制限（1 時間あたり、1 日あたり、1 通あたりの宛先数、そしてメールボックスと合わせた顧客の制限）のもとでメールボックスと同様に数え、メッセージを Postfix に渡します。Postfix で DKIM 署名が行われ、配送ログには web-<user ID> と表示されます。制限を超えて送信を試み続けるホスティングアカウント（スパムを送るハッキングされた Web サイト）は自動的にブロックされます。顧客のページには、アカウントとその件数が一覧表示され、ブロックの解除や設定ができます。サーバー上のプログラムは Postfix 自身の sendmail を使えず（root のみが使えます）、ポート 25 はローカルのプログラムを一切信頼しません。
